从本地仓库到 GitHub Pages：一次完整的发布

代码写完之后，发布才是最后一公里。这篇记录 ImageGrab 从 git init 到 https://hujiang888.github.io/imagegrab/ 真正可访问的过程，以及中间踩过的坑。

发布前先整理仓库 把过程切成提交 开启 GitHub Pages 三个真实的坑 验证，而不是假设

发布前先整理仓库

本地能打开，不等于线上能访问。发布前我做了三件事：确认 index.html 在站点根目录、 所有资源使用相对路径、把不需要上线的测试产物写进 .gitignore。

对纯静态站来说，这一步尤其重要。GitHub Pages 只负责托管文件，不会帮你修正路径或补上缺失的依赖。 一个大小写写错的文件名，在 Windows 上能打开，推到 Linux 构建环境就可能 404。

把过程切成提交

我没有把所有文件塞进一个“init”提交，而是按功能拆分：项目骨架、提取核心、下载逻辑、画廊、测试、官网、发布配置。 这样做的直接好处是，出问题时可以只回退某一块，而不是整个项目。 

git init -b main
git add .
git commit -m "feat: 图片提取核心与悬浮按钮"
git remote add origin https://github.com/hujiang888/imagegrab.git
git push -u origin main

提交信息写清楚“做了什么”，而不是“改了一下”。后者在三天后回看时几乎没有信息量。

开启 GitHub Pages

仓库创建好之后，Pages 不一定会自动工作。第一次部署时，Actions 里已经有 workflow 在跑， 但 Pages 还没有启用，部署任务最终失败。处理方式是先到仓库的 Settings → Pages 把构建来源配置好， 再重新触发一次部署。

对于放在 docs/ 目录的静态站，也可以直接选择“从分支部署”，目录选 /docs。 两种方式没有本质优劣：Actions 更灵活，分支部署更少配置。关键是**确认 Pages 的状态**，不要只看代码有没有 push 成功。

三个真实的坑

1. 中文被写成了 ???

用 PowerShell 5.1 调用 GitHub API 创建仓库时，中文描述被按错误编码发送，线上显示成了 ??? ImageGrab。解决方式是改用 UTF-8 字节发送 JSON，并重新 PATCH 仓库描述和 Release 说明。 这个问题的教训是：**涉及中文的 API 请求，必须显式指定 UTF-8**。

2. 构建成功不等于页面正确

部署状态变绿只能说明文件上传成功，不能说明页面没有 404。ImageGrab 的官网发布后，我又用浏览器实际打开， 检查了图片、CSS、下载 ZIP 和移动端宽度。线上验证要看“页面”，不能只看“部署日志”。

3. 缓存会骗你

Pages 有 CDN 缓存。修改后短时间内可能仍看到旧页面，尤其是 CSS 和图片。我的做法是： 先强制刷新，再用无痕窗口确认；如果仍然不对，再检查构建产物是否真的更新。

验证，而不是假设

发布完成后，我固定检查这几项：

  • 首页返回 200，HTTPS 正常；
  • CSS、JS、图片、下载文件都能打开；
  • 手机宽度下没有横向滚动；
  • 控制台没有报错；
  • 链接里的域名与仓库设置一致。

对个人项目来说，发布不是“把代码传上去”，而是“别人能稳定地打开它”。 这一步做完，项目才算真正完成。

写于 2026 年 10 月，ImageGrab v1.1.0 与个人网站发布之后。
