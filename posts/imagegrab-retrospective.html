19 张图里只留 11 张：一次相关性过滤的返工

“怎么无关的图片也加载进来了？”——这是 ImageGrab 第一版上线后收到的最直接反馈。 这篇记录我如何把“尺寸过滤”升级成“相关性过滤”，以及为什么最后保留了“全部”这个出口。

问题不是图太少 第一版：只看尺寸 把图片放回页面里 结果与取舍 留下的一条经验

问题不是图太少，而是太多

第一版 ImageGrab 的提取逻辑很直接：扫描页面上的 img、srcset、 data-src 和背景图，过滤掉小于 100px 的图标，然后把剩下的图片全部塞进画廊。 在模拟详情页里，它抓到了 19 张图：商品主图、细节图、推荐商品、买家秀、店铺横幅、优惠券二维码，一个都没落下。

对“批量下载”来说，图多似乎是好事。但用户打开画廊的第一反应不是“好全”，而是“怎么这些也进来了”。 这说明我解决的是**提取数量**，没有解决**提取意图**。商品图工具的默认结果应该是干净的，而不是让用户先做一次人工筛除。

第一版：只看尺寸，为什么不够

尺寸过滤能解决图标、logo 和占位图，但解决不了“大而无用”的图片。推荐商品的主图同样是 900×900， 买家秀同样是高清大图，广告横幅甚至更宽。它们在像素上完全合格，只是在页面语义上不属于当前商品。

我一开始想加关键词黑名单，比如文件名里带 banner、ad、avatar 就跳过。 但这只能覆盖一部分图片，而且很容易误伤。更可靠的做法，是回到图片所在的页面结构里去看。

把图片放回页面里

我给每张图增加了四类上下文判断，按优先级从高到低：

  1. 所在区域：祖先节点的 class / id 是否包含推荐、评价、广告、店铺装修等特征；如果在页头、页脚、侧栏，也直接排除。
  2. 链接指向：图片外层 <a> 是否指向另一个商品详情页。推荐位的图片经常点进去是别的商品，这是很强的信号。
  3. 图片比例：过宽或过扁的图通常是横幅；详情区的超长竖图则保留，因为那往往是商品细节长图。
  4. 替代文本与文件名：包含“试穿、模特、细节、实拍”等词加分；包含“图标、头像、二维码、推荐”等词减分。

简化后的判断逻辑大致是这样：

// 先排除，再判断是否属于商品图
if (inPageChrome(el)) return other('页面框架');
if (EXCLUDE_HINTS.test(h)) return other('推荐/评价/广告');
if (isForeignProductLink(href)) return other('其他商品');
if (aspect > 3.2 && !tallDetail) return other('横幅');

if (inGallery) return product('商品主图');
if (inDetail) return product('详情/试穿');
if (positiveAlt) return product('商品描述');
return other('位置不确定');

这里没有用任何视觉模型，全部是页面结构规则。它的好处是快、可解释、完全本地； 代价是规则需要跟着平台改版维护。对一个课程项目来说，这是合理的取舍。

结果与取舍

在模拟详情页的 19 张候选图里，默认视图现在只保留 11 张：商品主图、细节图、场景图和试穿图。 被排除的 8 张是推荐商品、买家秀、广告横幅和优惠券二维码。下载测试也从 11 张商品图全部成功导出为 PNG。

但我没有把“其他图片”彻底删掉。画廊顶部保留了「商品图 / 全部」切换：默认干净， 需要时仍能查看被过滤的内容并手动下载。因为“相关性”本身有判断误差，直接丢掉可能让用户永远找不回一张想要的图。

默认结果应该替用户做决定，但必须留一个可以反悔的出口。

留下的一条经验

这次返工让我意识到，过滤功能不是“规则越多越好”，而是**默认值 + 可恢复性**的设计问题。 规则负责把 80% 的噪声挡掉，界面负责让剩下的 20% 仍然可被找回。

如果你也在做类似的提取工具，建议先准备一个包含真实干扰项的测试页，再写规则。 只盯着主图写出来的过滤，通常会在推荐位和买家秀上翻车。
